**The following five design decisions have already been made by the user — implement
exactly these, do not re-litigate or second-guess them:**

1. **Stored score**: the `Match` row created by this feature stores the exact score
   the user saw in Smart Search at the moment they claimed it (the legacy scorer's
   result) — not a value recomputed via the Hybrid pipeline, and not both.
2. **Contact access**: once a user claims "this is my item," contact information
   becomes reachable **immediately** — do not gate it behind the other party's
   confirmation. (This is a deliberate product decision: speed of reunification
   matters more than requiring mutual confirmation first.)
3. **"Not my item" persistence**: this must be **permanently recorded**, not a
   session-local dismissal — the same pair must never be suggested to that user
   again in future searches.
4. **Entry point**: the claim action is available directly from the general
   `/search` results page (not only from a specific report's own page). If the
   claiming user owns more than one of their own reports, ask them which of their
   own reports this claim relates to as part of the flow.
5. **Security**: already handled separately in Phase 4 Part 2 — this task builds on

# TASK A — Backend: The Narrow "Claim" Capability (Decision #1)

1. Add a small, new application/domain method (e.g. on `MatchManager` or wherever the
   existing `Match`-creation/notification pattern lives — follow that existing
   pattern's shape and location, do not introduce a new architectural layer) that:
   - Takes the two report IDs (the search result's report, and the claiming user's
     own report) and the exact score the user saw in Smart Search.
   - If a `Match` row already exists for this exact pair, use it (do not create a
     duplicate — reuse the existing `ExistsForPairAsync`-style dedup pattern already
     used by background auto-matching).
   - If none exists, create one, with `SimilarityScore` set to the score the user
     actually saw (decision #1 — not a Hybrid-recomputed value), `IsAutoGenerated =
     false` (this is user-initiated, distinguish it from background auto-matches),
     and a `MatchReason` that honestly reflects it came from a user-initiated claim
     via search (do not fabricate the same reason text auto-matches use if it would
     be misleading).
   - Does NOT trigger the "whole candidate pool" recompute side effects that
     `RecomputeMatchesAsync` has — this must affect only the one specific pair the
     user chose.
2. Wire "this is my item" to: call the above to get/create the `Match`, then call
   the existing `AcceptAsync`-equivalent behavior — but per decision #2, do not gate
   Contact access on the other party's confirmation. Investigate whether calling the
   existing `AcceptAsync` directly already satisfies this (does `Match.Status =
   Accepted` alone unlock Contact today, with no dependency on the *other* party's
   separate action?) or whether the existing Accept flow's semantics need a small,
   honest adjustment to make one-sided claiming set the status correctly without
   misrepresenting it as a mutual decision. Reuse the existing notification
   side-effect (both parties get notified) unchanged.
3. Add a minimal way to persist "not my item" (decision #3) — investigate whether
   `MatchStatus.Rejected` on a `Match` row (using the same claim-creation method,
   just rejecting instead of accepting) is sufficient and already excludes that pair
   from resurfacing, or whether a small, additional field/flag is genuinely needed
   to distinguish "the searching user explicitly dismissed this" from other
   rejection scenarios. Keep this as small as possible — reuse `MatchStatus` if it
   already does the job.
4. Ensure a "not my item" pair is genuinely excluded from future search results for
   that specific user — trace this through the actual search candidate-retrieval
   path and confirm the exclusion is real, not just recorded and ignored.
