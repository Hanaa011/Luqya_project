## 1. Executive Summary

The current AI layer (`AI/`, `AI/Providers/`, `BackgroundJobs/ReportMatchingBackgroundJob.cs`) is a **working, reasonably well-documented, single-provider-at-a-time semantic search pipeline** built directly on top of one external LLM/embedding provider (Gemini by default, four alternates available). It already embodies several good instincts — deterministic scoring separated from AI calls, a provider-independent explanation layer, defensive JSON parsing, graceful degradation on classification failure — that the target architecture should preserve.

However, it is **not** the offline-first, provider-independent, knowledge-graph-driven platform described in `PHASE-1-PART-1`. Concretely:

- There is **no local semantic layer at all**. Every embedding — text and image — is generated by calling an external HTTP API. If every external provider is unavailable, search degrades to a raw-text fallback with zero embeddings and zero classification (see `AiMatchingService.ClassifySearchAsync` catch blocks) — the platform does not "continue operating with high quality," it continues operating with materially degraded quality.
- "Image embedding" is, for every provider, actually **caption-then-text-embed** — none of the five providers produce a true visual embedding. This is a semantic-quality ceiling, not an implementation bug.
- The "knowledge" the system has (`ObjectTypeRelationship`'s 5 clusters, `SearchTextProcessor`'s ~15-concept synonym map) is hand-written, English/Arabic-only, and does not scale — it is the seed the Knowledge Graph (Part 5) must absorb and replace.
- `AiMatchingService` (1,089 lines) is a God Class carrying five to six distinct responsibilities with no interfaces separating them, which is the single biggest structural blocker to the modular, replaceable architecture Part 4 requires.
- Provider resiliency is **inconsistent**: `GeminiVisionHelper` has real retry/backoff/timeout handling; the other four providers have none.

None of this means "start over." It means the deterministic scoring philosophy, the classification/embedding provider abstraction, and the explanation layer are worth keeping and hardening, while the AI-provider layer, the caching layer, and the "knowledge" layer need to move behind proper abstractions before Phase 2 can build the local-first stack on top of them.

## 2. File-by-File Review

### 2.1 `AI/AiMatchingService.cs` (1,089 lines)

| | |
|---|---|
| **Purpose** | Orchestrates one end-to-end search: classify → embed → fetch candidates → score → rank → explain. |
| **Responsibilities (actual)** | (1) Classification orchestration + timeout/fallback, (2) query embedding orchestration + caching, (3) candidate pre-filtering, (4) deterministic multi-signal scoring engine (10 score components + penalty + dynamic boosts), (5) result ranking, (6) translation of scores into explainable structured facts (`ReasonSummary`), (7) structured "reason chip" text generation. |
| **Dependencies** | `IEmbeddingProvider`, `IItemClassificationProvider`, `IReportRepository`, `ILogger` (injected) **+** `QueryProcessingCache`, `SearchTextProcessor`, `ConfidenceCalibrator`, `ObjectTypeRelationship`, `MatchExplanationGenerator`, `CosineSimilarityCalculator` (all static, compile-time coupled, not injected). |
| **Inputs** | Free-text query, optional image bytes, optional report-type filter, max results. |
| **Outputs** | `List<RankedReportResult>` (score, structured reasons, natural-language explanation). |
| **Violated principles** | **SRP** (7 responsibilities in one class). **OCP** (adding a new scoring signal, e.g. location/date, means editing `BuildCandidateScore`/`ScoringWeights` directly — both are already stubbed at zero, waiting for exactly this problem). **DIP** (five infrastructure concerns reached via `static` classes instead of interfaces — none of them can be swapped, mocked, or decorated). |
| **Redesign direction** | Split into: `IQueryClassificationService`, `IQueryEmbeddingService` (owns the cache), `ICandidateScoringEngine` (itself composed of pluggable `IScoreComponent`s), `IConfidenceCalibrator`, `IMatchExplanationService`. `AiMatchingService` becomes a thin pipeline coordinator over these interfaces — this is precisely the Part 4 "Query Processing / Ranking Engine / Confidence Engine / Explanation Engine" module boundary. |

### 2.2 `AI/AiSearchAppService.cs` (105 lines)

Thin ABP `ApplicationService`: validates input, decodes base64 image, delegates to `IAiMatchingService`, applies a `MinimumScorePercentage` post-filter, maps to DTO. Clean separation, correctly depends on the abstraction (`IAiMatchingService`), not a concrete class.

- **Minor SRP nit**: the minimum-score filter is a ranking/business rule currently living in the application-service (presentation-adjacent) layer rather than in the ranking engine itself. Low severity, but should move into the future `IHybridSearchEngine`/`IRankingEngine` so every caller (not just this one HTTP-facing service) gets consistent filtering.
- **Observability nit**: every field of every request/response is logged at `Information` level unconditionally (lines 30–35, 79–86). At production volume this is a non-trivial logging cost per search request and belongs at `Debug`, with `Information` reserved for start/finish/error events.

### 2.3 `AI/AIProviderOptions.cs` (80 lines)

Clean POCO options, one nested class per provider, bound from `LostFound:AI`. No violations. **Gap**: no `IValidateOptions<AIProviderOptions>` — a missing API key is only discovered when a provider is first called, deep inside a request, not at startup. This violates fail-fast/production-readiness expectations and should be closed in Phase 2A regardless of the larger redesign.

### 2.4 `AI/ConfidenceCalibrator.cs` (63 lines)

`internal static` piecewise-linear remapping of the raw 0–100 score onto a "reads right to a human" confidence band. Well-documented, monotonic by construction (so it never changes ranking, only display) — a genuinely good, keepable idea.

- **Violation**: not behind an interface; control points are hardcoded constants. Blocks the Part 4 "Confidence Engine" module (needs to be swappable/tunable without redeploy, e.g. per-tenant or per-locale calibration later).

### 2.5 `AI/LostFoundAiProvidersServiceCollectionExtensions.cs` (147 lines)

DI composition root: reads `LostFound:AI:Provider`, switches on a lowercased string to register the concrete `IItemClassificationProvider`/`IEmbeddingProvider`. Centralizes what used to be scattered — good improvement over the alternative.

- **Violation (OCP)**: adding a provider means editing this switch statement. A provider **registry** (keyed DI, or a small `IAiProviderCatalog` populated by each provider module) would let new providers (notably a future local ONNX/offline provider) register themselves without modifying this file — directly relevant to Part 1's "adding a provider must never require architectural redesign."

### 2.6 `AI/MatchExplanationGenerator.cs` (272 lines)

`internal static`, deterministic, provider-independent, no HTTP — the single best example in the codebase of "AI as enhancement, not owner": this used to be a second LLM round-trip per result (~15–20s) and is now instant, reproducible, local logic. Keep this pattern.

- **Violation**: language routing is a **binary** Arabic/English check (`LooksArabic`, a Unicode-range test). `BuildEnglish`/`BuildArabic` are two near-identical methods differing only in string literals — structural duplication that will not extend to Urdu, Hindi, Turkish, Persian, Malay, or French (all named as target languages in Part 1) without adding a third, fourth, fifth near-duplicate method. **Redesign direction**: a real `ILanguageDetector` + a template/resource-keyed localization strategy (one template, N resource sets), not per-language hand-written builder methods.

### 2.7 `AI/ObjectTypeRelationship.cs` (92 lines)

`internal static` hardcoded 5-cluster table (~25 object-type words) used both to early-filter obviously-wrong candidates and to tier the mismatch penalty. Cleanly written, well-reasoned defaults (unknown types are never penalized beyond the flat default, so a false cluster guess can't bury a real match).

- **Violation**: this is exactly the kind of hand-maintained taxonomy the Knowledge Graph (Part 5) is designed to replace and scale past "a few dozen types." It also has an **undocumented, unchecked coupling** to `ClassificationPromptBuilder`'s exact requested vocabulary (`"Smartphone"`, `"Wallet"`, `"Car"`, …) — if the prompt's vocabulary drifts, this table silently stops matching, with no compile-time or runtime signal. **Redesign direction**: object-type clustering becomes a Knowledge Graph query (`IS_A` / `RELATED_TO` traversal) instead of a static dictionary, removing the hidden string-contract between prompt and clustering table.

### 2.8 `AI/QueryProcessingCache.cs` (52 lines)

`internal static` `ConcurrentDictionary`-based cache for normalized query text and query embeddings, deliberately simple ("clear everything past 500 entries" instead of real LRU — acknowledged in the file's own comment).

- **Violations**: not DI-injectable (can't be replaced with `IMemoryCache`/`IDistributedCache`, can't be mocked in tests, can't carry per-tenant policy). **Strictly per-process** — cache is cold on every restart and does not share across horizontally-scaled instances, which directly conflicts with the Part 1 NFR "horizontally scalable." No hit-rate metrics. **Redesign direction**: `IQueryProcessingCache` abstraction over `IDistributedCache` (or a local `IMemoryCache` decorated with a distributed layer later), with real LRU/TTL eviction and cache-hit telemetry.

### 2.9 `AI/SearchTextProcessor.cs` (261 lines)

`internal static`, pure-function pipeline: Arabic letter-form normalization → punctuation strip → lowercase → drop intent words ("lost"/"found" and Arabic equivalents, correctly kept separate from object identity) → drop stopwords → synonym expansion (~15 concepts) → dedupe. Genuinely good design instinct (intent words must never affect similarity — this is called out and handled correctly) and, being pure functions, is easily unit-testable even without DI.

- **Violations**: hardcoded, tiny (~15 concepts) synonym map; **no Urdu support at all** despite Urdu being a native target language in Part 1; naive whitespace tokenization (no real tokenizer/lemmatizer/stemmer — Parts 3/6 must select one); not configurable/extensible without a code change + redeploy, which directly contradicts Part 1 Principle 5 ("adding a language must never require architectural redesign").

### 2.10 AI Providers (`AI/Providers/*.cs`, 14 files)

Reviewed as a group; provider-specific notes follow.

**Shared good pattern**: `ClassificationPromptBuilder` (70 lines) centralizes one prompt/JSON-contract for every text-capable provider — a real DRY win versus the alternative (5 diverging prompts). `ClassificationJsonParser` (129 lines) is defensively written: tolerates markdown code fences, uses `TryGetProperty` throughout, and **never throws** — it degrades to `"Uncategorized"` on any parse failure. Both are good, keepable infrastructure.

**Shared problems**:

- **Inconsistent resiliency.** `GeminiVisionHelper` (389 lines) has real exponential backoff, per-attempt timeouts, transient-status-code detection (429/500/502/503/504), and a rich `GeminiApiException`. **None** of `OpenAIVisionHelper`, `OllamaVisionHelper`, `HuggingFaceClassificationProvider`, or `DeepSeekVisionHelper` retry anything — each is a single `EnsureSuccessStatusCode()` away from throwing a bare exception on any transient failure. This is the single biggest "Provider Review" finding: the abstraction (`IItemClassificationProvider`/`IEmbeddingProvider`) promises interchangeable providers, but only one implementation is actually production-hardened.
- **No circuit breaker.** No Polly (or equivalent) anywhere. A slow/degraded provider can stall requests up to whatever the ambient `HttpClient` timeout is (embeddings have **no** explicit timeout at all in `AiMatchingService` — only classification gets the 20s `CancellationTokenSource`).
- **Inconsistent config validation.** Gemini checks `ApiKey` + model name before calling; OpenAI and HuggingFace do not check `ApiKey` at all before using it (a missing key surfaces as an opaque 401 from the wire, not a clear local error).
- **LSP-adjacent behavioral gap.** `HuggingFaceClassificationProvider` explicitly documents itself as best-effort/degraded relative to the others (falls back to category-only classification, no `searchText`, when its generative attempt fails — which the file says can happen often on the free tier). `DeepSeekVisionHelper` silently ignores `imageBytes` entirely. Substituting these providers for Gemini is **not** behavior-preserving, which weakens "provider independence" as an actual guarantee rather than an aspiration.
- **"Image embedding" is caption-then-text-embed everywhere.** `GeminiEmbeddingProvider.GenerateImageEmbeddingAsync`, `OllamaEmbeddingProvider`, `HuggingFaceEmbeddingProvider`, and `OpenAIEmbeddingProvider` (via `OpenAIVisionHelper.CaptionImageAsync`) all caption the image with a vision-capable LLM call, then embed the resulting caption text. There is no true joint image embedding (e.g. CLIP/SigLIP-style) anywhere in the system. Two visually distinct objects that happen to get similarly-worded captions will score as near-identical on `ImageScore` — a real semantic-quality ceiling, not a bug, and squarely a Part 3/6 research question.
- **No shared HTTP base/decorator.** Each classification provider re-implements the same "build request → POST → parse via shared parser" skeleton. A `ResilientProviderDecorator` (wrapping any provider with uniform retry/timeout/circuit-breaker) or a shared abstract base class would remove this duplication and — more importantly — fix the resiliency inconsistency in one place instead of five.

### 2.11 `BackgroundJobs/ReportMatchingBackgroundJob.cs` (220 lines)

Orchestrates the full post-create/update pipeline: load report → load image blob → classify → resolve/create category → apply classification to entity → build embedding text → generate text embedding → generate image embedding → save → run matching.

- **Violation (SRP)**: one ~150-line method mixing blob I/O, classification, category resolution, two embedding calls, persistence, and matching orchestration. A staged pipeline (Chain of Responsibility, or a small in-process mediator over discrete steps) matches the Part 4 "modular pipeline" target and would make each stage independently testable.
- **No partial-progress checkpointing.** If classification succeeds but the embedding call then fails, a retry (per ABP's background job retry semantics) re-runs classification from scratch — wasting a paid AI call. Worth addressing in the Part 9 migration/rollout design, not necessarily in Phase 1.
- **Logging severity misuse.** Routine step-tracing is logged at `LogCritical` (lines 54–57, 63, 69 …) — `LogCritical` conventionally pages/alerts in production monitoring. Only the actual failure path (line 207) should be `Critical`; the rest should be `Information`/`Debug`.

### 2.12 `Reports/ReportAppService.cs` (177 lines)

Clean CRUD `ApplicationService`. Correctly re-triggers the background job only when description/image/location actually changed (not on every update, e.g. a pure status change). No significant violations found.

## 3. Architecture Problems (Summary)

1. **No offline/local semantic layer exists.** Every embedding and every classification is a network call to an external provider. This is the central gap the rest of Phase 1 (Parts 4–8) exists to close.
2. **`AiMatchingService` is a God Class** with no internal seams — the biggest blocker to the "independently replaceable" module boundaries Part 4 requires.
3. **Five "local, deterministic" concerns are static classes, not injectable abstractions** (`ConfidenceCalibrator`, `ObjectTypeRelationship`, `SearchTextProcessor`, `MatchExplanationGenerator`, `QueryProcessingCache`) — none are swappable, decoratable, or unit-mockable at the seam a consumer would want.
4. **Provider resiliency is a one-off, not a policy** — only Gemini's helper retries; the DI/config layer offers no way to apply a uniform resiliency policy to whichever provider is configured.
5. **"Knowledge" is a handful of hardcoded tables** (5 clusters, ~15 synonym groups) tightly, invisibly coupled to the LLM prompt's exact vocabulary — brittle and non-scalable by construction.
6. **Multilingual support is binary (Arabic/English) and hardcoded**, not a designed capability — Urdu (a stated native target language) has no support anywhere in the query pipeline.
7. **Caching is process-local and unbounded-then-cleared** — works for a single instance today, breaks the "horizontally scalable" NFR the moment there's more than one instance.
8. **"Image embedding" has no true visual signal** in any provider — a caption-then-text-embed shortcut across the board.

### 4.2 Circular Dependency Analysis

**None found.** Flow is strictly one-directional: `AppService → MatchingService → Provider abstractions → concrete Providers`, and `BackgroundJob → Provider abstractions → concrete Providers` in parallel. This is a genuine strength to preserve.

### 4.3 Provider Dependency Map

`AIProviderOptions:Provider` (string, case-insensitive) selects **both** the classification provider and — unless `EmbeddingProvider` is separately set — the embedding provider, resolved once at startup in `LostFoundAiProvidersServiceCollectionExtensions`. DeepSeek is the one asymmetric case: it has no embeddings API, so it always requires (or defaults to) a separate `EmbeddingProvider`. There is no runtime provider switching, no per-request provider override, and no multi-provider fallback chain (e.g. "try Gemini, fall back to OpenAI") — the Part 1 "Cached AI → External AI" fallback ladder does not exist today; there is exactly one active provider at a time, and if it fails, the pipeline falls back straight to raw-text search, skipping every intermediate tier the target architecture calls for.

### 4.4 Runtime Dependency Flow

**Search request**: `AiSearchAppService.SearchAsync` → `AiMatchingService.FindSimilarReportsAsync` → `ClassifySearchAsync` (external call, 20s bound, degrades to empty on failure) → `GenerateQueryEmbeddingsAsync` (external call(s), **no bound**, cache-checked first) → `IReportRepository.GetSearchableReportsAsync` (loads **all** candidates matching the type filter into memory) → `ScoreCandidates` (in-memory, CPU-only, single-threaded loop) → `BuildRankedResults` (in-memory, deterministic).

**Report create/update**: `ReportAppService.CreateAsync`/`UpdateAsync` → enqueue `ReportMatchingBackgroundJobArgs` → `ReportMatchingBackgroundJob.ExecuteAsync` (external classify call → external text-embed call → external image-embed call → save → `MatchManager.FindAndCreateMatchesAsync`, a **second**, structurally separate matching path from `AiMatchingService`).

**Recommendation flagged for Part 4/9**: the existence of two independent matching code paths (`AiMatchingService` for interactive search, `MatchManager` for background auto-matching, not reviewed here as it's outside `AI/`) is worth explicit reconciliation — if `MatchManager` duplicates scoring logic rather than reusing the same engine, that is a second, silently-diverging copy of the ranking rules.

## 5. SOLID Audit

| Principle | Verdict | Evidence |
|---|---|---|
| **Single Responsibility** | **Fails** | `AiMatchingService` (§2.1) owns 7 responsibilities. `ReportMatchingBackgroundJob.ExecuteAsync` (§2.11) owns 6+ pipeline stages in one method. |
| **Open/Closed** | **Fails** | Adding a scoring signal requires editing `AiMatchingService.ScoringWeights`/`BuildCandidateScore` (§2.1). Adding a provider requires editing the DI switch statement (§2.5). Adding a language requires editing `SearchTextProcessor`/`MatchExplanationGenerator` source (§2.6, §2.9). |
| **Liskov Substitution** | **Weak** | `IItemClassificationProvider` implementations are not behaviorally interchangeable — HuggingFace and DeepSeek both self-document reduced capability versus Gemini/OpenAI/Ollama (§2.10). Swapping providers changes result quality, not just latency/cost. |
| **Interface Segregation** | **Mostly fine** | `IEmbeddingProvider`/`IItemClassificationProvider` are small, focused interfaces (not reviewed directly — inferred from usage — but no evidence of fat/unused-method interfaces). |
| **Dependency Inversion** | **Fails** | Five infrastructure concerns are reached via `static` classes instead of interfaces from within `AiMatchingService` (§2.1, and repeated at §2.4, §2.6–2.9 individually). This is the single most consistent violation across the codebase. |

## 6. Performance Findings

- **Full in-memory candidate scan, every search.** `GetSearchableReportsAsync` loads every candidate report matching the type filter; `ScoreCandidates` then runs cosine similarity (text + image) plus 8 more score components per candidate, single-threaded, synchronously. Fine at hundreds of reports; will not hold at the "millions" scale Part 1 targets — there is no vector index (ANN/FAISS-style) anywhere.
- **No caching of decoded candidate embedding vectors.** Every scored candidate implies deserializing its stored embedding (`GetEmbeddingVector()`/`GetImageEmbeddingVector()`, defined on `Report`, outside this file set) from its persisted JSON form, per request. Repeated, avoidable allocation on the hot path.
- **Query embedding is cached; candidate embeddings are not.** `QueryProcessingCache` only caches the one query-side embedding per unique normalized query — the N candidate-side embeddings are re-parsed from JSON every single request.
- **Unbounded classification/embedding latency for embeddings.** Classification has a hard 20s timeout with graceful fallback (§2.1); embedding calls have **no** timeout or cancellation bound in `AiMatchingService` at all — a slow provider stalls the whole request indefinitely (bounded only by the ambient `HttpClient` default, which is not overridden anywhere reviewed).
- **Verbose `Information`-level logging on every field of every request** (`AiSearchAppService`, and pervasively via `LogInformation`/`LogCritical` throughout `AiMatchingService` and `ReportMatchingBackgroundJob`) — real I/O cost per request at scale; not yet a bottleneck at current traffic, but flagged for Part 4's Observability design (structured, sampled, level-appropriate logging).

**Estimated improvement potential** (qualitative, to be quantified once Part 6/7 select concrete technology): moving candidate retrieval behind a real vector index removes the dominant O(N) cost as report volume grows past low thousands; caching decoded candidate vectors removes repeated JSON parsing entirely; a uniform provider timeout/circuit-breaker bounds worst-case request latency instead of leaving it to chance.

## 7. Concurrency Findings

- **Thread safety**: `AiMatchingService` is `ITransientDependency` (new instance per resolution) with no instance-level mutable state — safe. The shared mutable state lives entirely in the `static` caches (`QueryProcessingCache`), which correctly use `ConcurrentDictionary` — genuinely thread-safe, but with a crude "clear everything past 500 entries" policy under concurrent load (a burst of unique queries near the cap can cause a full-cache wipe mid-request-storm, followed by a thundering herd of cache misses).
- **Async correctness**: generally sound — `async`/`await` used consistently, no observed `.Result`/`.Wait()` blocking calls, no observed `async void`.
- **Cancellation token propagation is incomplete.** `AiMatchingService.FindSimilarReportsAsync` takes no `CancellationToken` parameter at all, so a client disconnect / request abort cannot cancel an in-flight search — the only cancellation in the whole search path is the internally-constructed 20s classification timeout (§2.1), which is unrelated to caller cancellation.
- **No parallelization of independent work.** `ScoreCandidates` scores candidates sequentially even though each candidate's score is fully independent of every other's — an embarrassingly parallel loop currently run single-threaded. Not a correctness issue, purely a missed throughput opportunity worth revisiting once candidate volume grows (Part 7).

## 9. Search Quality Findings

- **Normalization** (`SearchTextProcessor`): correctly separates report-intent words from object-identity words (a genuinely good, non-obvious design decision — "lost iPhone" and "found iPhone" must score identically on the object, and they do). Coverage is thin (~15 concepts, 2 languages) relative to the Part 1 vision.
- **Classification**: quality is provider-dependent and, per §8, inconsistent across providers — the `searchText` field (the one thing actually embedded) is only reliably rich for Gemini/OpenAI/Ollama; HuggingFace/DeepSeek degrade it.
- **Embeddings**: text embeddings are real; image embeddings are caption-derived text embeddings everywhere (§2.10) — a structural ceiling on visual match quality.
- **Semantic matching**: cosine similarity on provider-generated embeddings, no hybrid retrieval (no BM25/exact-match/fuzzy layer combined with the embedding signal) — a single-signal similarity score is the sole text-relevance input, weighted at 55% (`ScoringWeights.TextWeight`) alongside hand-tuned attribute bonuses/penalties.
- **Confidence calculation**: `ConfidenceCalibrator`'s piecewise-linear remap is a solid, monotonic, keepable idea — but it is calibrated once, by inspection, with no feedback loop from actual match outcomes (no relevance-labeled evaluation set exists in this codebase to validate the control points against).
- **Explanation generation**: high quality relative to its cost (deterministic, instant, bilingual) — but "bilingual" is presently a hardcoded binary, not the multilingual design the vision calls for (§2.6).

**Overall verdict**: the deterministic scoring/explanation approach is a strong foundation; the semantic input feeding it (embeddings, knowledge/synonym coverage, hybrid retrieval) is the part most in need of the Phase 1 Parts 3, 5, 6, 7 redesign.

## 11. Refactoring Priorities

1. **Introduce abstractions for the five static local components** (`IConfidenceCalibrator`, `IObjectTypeRelationship`/knowledge lookup, `IQueryTextProcessor`, `IMatchExplanationService`, `IQueryProcessingCache`) — unblocks everything else; lowest-risk, highest-leverage change, and directly matches the Part 4 interface inventory (`IConceptResolver`, `IRankingEngine`, etc.).
2. **Decompose `AiMatchingService`** into a pipeline of the above abstractions plus a scoring engine composed of pluggable `IScoreComponent`s.
3. **Unify provider resiliency** behind one decorator/policy applied to all five providers.
4. **Add `IValidateOptions` startup validation** for provider configuration (cheap, immediate production-readiness win, no architectural risk).
5. **Fix logging severity** in `ReportMatchingBackgroundJob` (cheap, immediate operational win).
6. Everything else (Knowledge Graph, true local embeddings, hybrid retrieval, multilingual expansion) depends on (1)–(3) existing first, and is properly the subject of Parts 4–9.

## 12. Recommended Target Architecture (Preview)

This section is intentionally brief — the full target architecture is Part 4's deliverable. Directionally: `AiMatchingService` becomes a thin **Query Processing** coordinator over an **Abstractions** layer (the interfaces in §11.1) that is backed, in Phase 2A/2B, by **Infrastructure** implementations — some remaining external-provider-backed, some newly local (Knowledge Graph lookups, local embeddings) — with the current static classes' *logic* largely preserved but relocated behind those interfaces rather than rewritten from scratch. This satisfies both the CLAUDE.md instruction to prefer improving existing implementation over replacing it, and the Part 1 mandate that business logic never reference concrete providers directly.
